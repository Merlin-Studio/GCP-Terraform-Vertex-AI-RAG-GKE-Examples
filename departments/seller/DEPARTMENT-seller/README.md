# Department: Seller Platform (`seller`)

Generated by Merlin Studio for Cloud Foundation Fabric v58.0.0.

A department is the unit workloads sit in: a business unit with its own team
and its own data, whose developers must not reach another department's data,
even in dev. This bundle is that department as an **increment** on the
landing zone you have: Terraform roots applied on top of it, creating what the
department needs and touching nothing the landing zone's state owns.

## What it never touches

The landing zone's folders, projects, networks, policies and perimeter are
read by name and never changed. Every attachment to something that exists is
a resource of its own: a subnet in a network, an IAM member on a subnet, a
policy attached to the department's folder.
Destroying this department removes what it created and nothing else.

## Before applying

The facts in each root's `terraform.tfvars` came from the confirm table: the
network project and its networks, the key project, the region.

Two facts only your organisation knows, and Merlin never asks for them: the
billing account, which is confidential, and the folder numbers, which exist
only once the landing zone is applied. This bundle carries Merlin's
placeholders for them (`FAKE00-...`, `folders/0...`). Their one home is
`deploy/seller.facts.env`: put the real values there. The apply script passes
them to every root, so no `terraform.tfvars` needs an edit.

`deploy/preflight-seller.sh` checks every fact against your organisation,
refuses a placeholder, and checks that the identity running it may create
what the roots create. Run it first; `deploy/apply-seller.sh` runs it for you.

The groups are prerequisites, not created here: `gcp-seller-developers@vendora.eu` (developers), `gcp-seller-qa@vendora.eu` (qa), `gcp-seller-owners@vendora.eu` (owners).
Set `create_groups` and the Cloud Identity customer id in the department to
have the core root create the team groups instead.

## Apply

```bash
./deploy/apply-seller.sh /path/to/fabric-checkout            # preflight, core, then each environment
./deploy/apply-seller.sh /path/to/fabric-checkout --plan-only
```

The core root runs first with local state and moves its state into the
bucket it created, the way FAST's bootstrap does. Each environment root reads
what core created from `core.auto.tfvars.json`, which the script writes from
core's outputs, so no root reads another's state.

## How applications use it

`MERLIN_DEPARTMENT.json` records the department's projects, subnets, key
ring and deploy identities. An application that chooses this department is
placed against that record: its services in `vd-seller-app-<env>-0`,
its data in `vd-seller-dp-<env>-0`, on the department's subnet.

## Merlin's opinions, recorded as such

- The subnet is a /22 per environment from `10.200.0.0/16`, clear of every
  range the landing zone recorded. Change `subnet_cidr` if your address plan
  says otherwise.
- Developers change non-production and read production; owners administer
  non-production and read production; QA reads. The DBA group administers
  the data project's databases, the network group reads networking, the
  security group reviews IAM. Edit `iam_by_principals` in the environment
  roots if your organisation draws the lines elsewhere.
- The firewall policy allows the department's own range, Google's health
  checks, and SSH/RDP through Identity-Aware Proxy. It denies nothing: what
  the landing zone denies above it stays denied.
- The state bucket is not encrypted with a customer-managed key: state
  holds identifiers, and a bucket that needs a key before it exists is a
  circular start.
