# Deploying these workloads

Merlin does not apply anything. It compiled these stages against one landing
zone and handed them over; your pipeline runs them. This is what that takes.

Generated for Cloud Foundation Fabric `v58.0.0`, from landing-zone job `c1c0cfb4-afd2-45a9-be67-35f18aa014b9`.

## Before the first run

You need the Fabric checkout that holds your deployed landing zone, with its
stages already applied: `0-org-setup`, `1-vpcsc` if you use it, `2-networking`,
`2-security`, `2-project-factory`. You also need the tfvars those stages publish
to the `iac-outputs` bucket, and the provider file `0-org-setup` writes for each
workload stage. `fast-links.sh` in the checkout fetches both.

Then check the bundle against the checkout:

```bash
./deploy/verify.sh /path/to/fabric-checkout
```

This compares the fingerprint of the landing zone these workloads were compiled
against with the one in the checkout. **If it refuses, stop.** Every stage below
references projects, networks and keys by name, resolved from one landing zone.
Applied onto a different one they either miss those names or hit something that
happens to share one. The fix is to regenerate the workloads in Merlin from the
landing zone you actually deployed, not to skip the check.

## Applying

```bash
./deploy/apply.sh /path/to/fabric-checkout --plan-only   # read the plans first
./deploy/apply.sh /path/to/fabric-checkout               # plan, then apply
```

`deploy/Jenkinsfile.example` does the same thing one stage at a time, with an
approval before each apply. `deploy/stages.env` is the plan as data, if you
would rather drive it from your own tooling.

The shared registry goes first, because services pull images from it.
Then environment by environment, non-production before production, so a
mistake surfaces somewhere cheap. Inside an environment the data platform runs
before the services that use it.

Each stage runs as its own deploy identity with its own state prefix, both
provisioned by the landing zone. A dev stage cannot reach production state even
if someone runs it with the wrong credentials to hand.

### The data platform stages are not Terraform roots

`3-data-platform-*` is a project-factory *dataset*. It is copied into
`2-project-factory/datasets/` and applied by running that stage against it with
its own `terraform.tfvars`, which sets a separate `stage_name` so it gets its
own state. The project it fills is reused, never recreated. `apply.sh` handles
this; if you drive the stages yourself, do not try to `terraform init` inside a
data-platform folder.

## Re-running after a change in Merlin

Regenerate the workloads, download the new bundle, and replace this folder.
Unchanged entries produce identical files, so `terraform plan` shows only what
you actually changed. Review that plan rather than the diff of the bundle.

If you changed the landing zone as well, regenerate it first and apply its
stages, then regenerate the workloads against it. `verify.sh` will refuse the
old workload bundle against the new landing zone, which is the intended
behaviour and not something to work around.

## Removing a workload

Dropping an entry in Merlin removes its files from the bundle. Terraform reads
that as a resource to destroy, and the next `apply` will destroy it. Read the
plan before approving: for a database or a bucket that is a deletion of data,
and the plan is the last place it can be stopped.
