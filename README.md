# Production Terraform for GCP: Vertex AI RAG, GKE microservices, Cloud Run + Cloud SQL, and a MySQL migration — inside one real company

[![terraform validate](https://github.com/Merlin-Studio/GCP-Terraform-Vertex-AI-RAG-GKE-Production-Examples/actions/workflows/validate.yml/badge.svg)](https://github.com/Merlin-Studio/GCP-Terraform-Vertex-AI-RAG-GKE-Production-Examples/actions/workflows/validate.yml)

Every tutorial shows you RAG in a sandbox: one project, the default service
account, a public endpoint. **This repository is the same four workloads the way
they look inside a company** — on a Shared VPC they do not own, in their own
department's projects, each service running as its own identity, private by
default, with customer-managed keys on everything that holds state.

It is one fictional company's whole Google Cloud estate as Terraform: the cloud
foundation, two departments, and four applications on top. **131 Terraform files
among 342 generated ones, and none of them written by hand.**

That fetches the Cloud Foundation Fabric modules these stages are built on and
runs `terraform init -backend=false` and `terraform validate` — about a minute
from a cold start, needing only `terraform` and `git`. **No credentials, nothing
created, nothing to clean up.** Leave the argument off to validate all 32

This is deliberately not a one-line `terraform apply`. A Vector Search endpoint,
a highly-available Cloud SQL instance and a GKE cluster are not things to create
from a stranger's repository to see what happens, and a version stripped down
until that was safe would be the sandbox demo this repository exists to be the
alternative to. To get a version you *can* apply, shaped for your own

## What makes these "production" rather than "demo"

**Every IAM grant is traced to a reason.** Each application stage carries a table
like this one, from the RAG example — a role exists because an arrow in the
architecture needs it, and for no other reason:

| Identity | Role | On | Because of |
|---|---|---|---|
| `seller-assistant-embedding-prd` | `roles/storage.objectViewer` | the corpus bucket | `objects -> embeddings` |
| `seller-assistant-embedding-prd` | `roles/aiplatform.user` | the vector index | `embeddings -> vectors` |
| `seller-assistant-api-prd` | `roles/aiplatform.user` | the vector index | `api -> vectors` |
| `seller-assistant-api-prd` | `roles/aiplatform.user` | the model guardrail | `api -> llm` |

Roles are granted on the resource wherever Google offers a resource-scoped form
— the two that have none, `dataflow.worker` and `bigquery.jobUser`, are on the
project and the table says so — and nothing runs as a default service account.

**The customer-managed key follows state, not the application.** In the RAG
example the corpus bucket, the vector index and the topic are encrypted with keys
from the central key project; the Cloud Run services and the load balancer are
not, because they hold nothing. See [`applications/CONFORMANCE.md`](applications/CONFORMANCE.md),
which lists every resource with its project, network, region and key.

**An application exists only where the foundation can host it.** The migration
example reaches back into the datacentre, and only the production network has the
VPN. So it was generated for production alone, and the bundle says why:

> Application 'inventory-replica' is generated for prd only, not dev, stg:
> `vpc-shared-dev` has no path to the landing zone's private-network link.

That is [`applications/VALIDATION_WARNINGS.md`](applications/VALIDATION_WARNINGS.md),
not an error message somebody wrote for this README.

**The Terraform explains itself.** From the migration job:

```hcl
# Copy what is already there, then follow changes. The one-time mode is a
# migration: it copies once and stops, which reads as a working replica
# until someone queries a row that changed afterwards.
type = "CONTINUOUS"
```

**Nothing confidential was needed to produce it.** Billing account and folder
numbers are placeholders; [`applications/PLACEHOLDERS.md`](applications/PLACEHOLDERS.md)
lists every value that has to be yours, and a preflight script per stage checks
them *before* an apply rather than after.

## How the repository is laid out

```
foundation/                 the cloud foundation: organization, Shared VPCs, VPN,
                            keys, VPC Service Controls, project factory
departments/
  shop/                     Storefront & Customer: its projects, subnets, key ring,
  seller/                   budget and deploy identities — added on top of the
                            foundation, touching nothing it owns
applications/
  3-app-<name>-<env>/       one Terraform root per application per environment
  3-app-<name>-delivery/    its delivery pipeline
  3-gke-<env>/  3-data-platform-<env>/  3-services-<env>/
  deploy/                   preflight, apply and verify scripts, a runbook
  CONFORMANCE.md            every resource: project, network, region, key, and why
examples/                   the four pages linked above
scripts/validate.sh         validates every Terraform root against Fabric; CI runs it
```

The three layers are separate on purpose. A department is an *addition* to a
foundation that already exists — new projects, a subnet per environment, a key
ring, a budget — and an application lands in its department's projects while the
cluster and the network stay shared.

| Application | Department | Environments |
|---|---|---|
| `seller-assistant` (RAG) | `seller` | dev, stg, prd |
| `storefront` (GKE) | `shop` | dev, stg, prd |
| `checkout` (Cloud Run + analytics) | `shop` | dev, stg, prd |
| `inventory-replica` (migration) | `seller` | prd only — see above |

## Before you apply

This is a [FAST](https://github.com/GoogleCloudPlatform/cloud-foundation-fabric/tree/master/fast)
estate, and FAST changes what "prerequisites" means. There is no list of APIs to
enable by hand and no list of roles to grant a person — and a README that gave
you one would be describing a different kind of repository.

- **APIs are enabled by the foundation, per project.** Each project's file in
  [`foundation/project-factory`](foundation/project-factory) declares its
  `services:`, and the project factory turns them on. The data projects get
  BigQuery, Dataflow, Pub/Sub, Cloud SQL and Storage that way, not from a
  checklist.
- **Stages are applied by identities the foundation creates, not by you.** Each
  stage has a named deploy identity — `iac-gke-prd`, `iac-app-dev`,
  `iac-app-delivery`, `iac-<department>-<env>` — and
  [`applications/deploy/RUNBOOK.md`](applications/deploy/RUNBOOK.md) lists every
  stage, in order, with the identity that runs it.
- **A person needs elevated rights once, for the first stage only:** Organization
  Administrator and Billing Account Administrator, to bootstrap the
  organization. See [`foundation/DEPLOYMENT_GUIDE.md`](foundation/DEPLOYMENT_GUIDE.md).

What you do need:

| | |
|---|---|
| Tools | `terraform` >= 1.12.2, `gcloud`, `git` |
| Fabric | a checkout of Cloud Foundation Fabric at `v58.0.0` — the stages reach its modules by relative path, from `fast/stages/` |
| Your facts | the billing account and the folder numbers, in **one file per department**: [`departments/shop/deploy/shop.facts.env`](departments/shop/deploy/shop.facts.env). Anything beginning `FAKE00-` or `folders/0` is a placeholder. No `terraform.tfvars` needs editing |
| The rest | [`applications/PLACEHOLDERS.md`](applications/PLACEHOLDERS.md) — container images, the VPN peer address, the source database's host and credentials |

The order is foundation, then departments, then applications, and each layer
checks itself before it creates anything:

1. **Foundation** — the FAST stages, in the order [`foundation/DEPLOYMENT_GUIDE.md`](foundation/DEPLOYMENT_GUIDE.md) gives.
2. **Departments** — `deploy/preflight-shop.sh`, then `deploy/apply-shop.sh`. The
   preflight is read-only: it checks every fact against your real organization,
   and uses `testIamPermissions` to confirm the identity running it may create
   what the roots create.
3. **Applications** — `deploy/verify.sh /path/to/fabric-checkout`, a
   `preflight-<stage>.sh` per stage, then `deploy/apply.sh`, as the runbook lays
   out.

## The company

**Vendora** is fictional: an EU online marketplace about eighteen months into
moving off its own colocation facility, with the old monolith's MySQL still the
system of record. That is why there is a VPN, why there is a migration, and why
the two halves have to work at once. The domain, the names and the addresses are
invented.

The foundation is built on [Cloud Foundation Fabric FAST](https://github.com/GoogleCloudPlatform/cloud-foundation-fabric)
in `europe-west4`, three environments, with customer-managed keys, VPC Service
Controls and Cloud Armor. It was generated under NIS2, GDPR, ISO 27001 and CIS —
and the honest finding is how little that changed at the application level: the
defaults were already private, dedicated-identity and logged, so the frameworks
mostly confirmed what was going to be generated anyway. The scorecards are in
[`foundation/`](foundation): security 91/100, architecture 98/100.

## What this is not

- **Not deployable as-is.** The stages reference a foundation that has to exist in
  your own organization, the container images are placeholders until your pipeline
  publishes one, and the peer VPN address is a documentation address.
- **Not your application.** Each stage is the platform an application lands on.
  Chunking strategy, prompts, schemas, routes and handlers are yours, and each
  stage README says exactly which.
- **Not a certificate.** A row saying a setting was required by a framework means
  a rule mapped to that framework forced it, with the reference printed beside it
  so it can be checked.
